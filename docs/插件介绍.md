# 微信通道插件 · dsh-channel-wechat-bg

> 由 **DSH（DeepSeek Harness）** 制作：会话、人格、模型、工具与权限都归 DSH 管，
> 这个仓库只做一件事——**把微信接成 DSH 的一条通道**。
>
> 一句话：**让你的 AI 伙伴住进你的微信里**——它能收到你发给它的消息，也能像人一样
> 打字回复你；但只对名单上的会话开口，别人说话它一律装死。
>
> 这篇既是"它替我做什么"的说明，也是"它怎么工作、出问题怎么查"的技术文档。
> 前半部分不需要懂代码，后半部分给接手维护的人。

---

## 一、它解决的是什么问题

现在的 AI 伴侣大多活在浏览器或独立 App 里：你想找它，得切窗口、点开对话框。
而人真正在的地方是微信。

接上之后，你在微信里给一个号发消息，AI 用它自己的人格回你；你在群里 `!` 一下，
它也会冒泡。就像给微信装了一个会思考的聊天对象。

它最特别的地方是一句听起来有点怪的话：

> **收消息完全后台，发消息占前台。**

## 二、为什么"收"和"发"要分开说

微信个人号没有开放接口。想让它自动收发，四条路都试过：

| 路线 | 结果 |
| --- | --- |
| 协议注入（WeChatFerry） | **不可用**。绑定微信 3.9.x 的固定偏移，而腾讯已对 3.9.x 返回「当前微信版本过低」拒绝登录 |
| 第三方 Pad 协议（付费） | 技术上可行，但要付钱、要交出登录态，封号风险不可控 |
| 官方能力（公众号 / 企业微信） | 只能用自己的号，做不了"以我的身份和朋友们说话" |
| UI 自动化（本插件采用） | 唯一能在现役微信 4.x 上跑通的路；代价是必须有一个窗口在前台 |

UIA 的代价很具体：把微信窗口拎到最前、把文字粘进输入框、点发送，然后把窗口还回去。
整个过程一两秒，但确实发生了——你会看见窗口跳一下，键盘被临时接管。

于是核心设计就出来了：既然必须占前台，就**不让它占你的前台**。

```
        ┌──────────────── 你的电脑 ────────────────┐
        │  DSH（AI 在这里思考）                     │
        │      ↕ HTTP / 事件流                     │
        │  桥    （Python 程序）                    │
        └───────────────┬──────────────────────────┘
                        │
        ┌───────────────▼──────────────────────────┐
        │  虚拟机（另一台"电脑"，你在用的时候看不见） │
        │   微信 4.x  ← 桥在这里点它、读它的库       │
        └──────────────────────────────────────────┘
```

**把"抢前台"关进虚拟机**。微信和那套自动化跑在 VMware 里，被抢的是虚拟机的前台——
你在宿主机上打游戏、看视频、写代码，一点都碰不到。

## 三、架构

```
宿主（Windows）
└─ DSH  …  plugin dsh-channel-wechat-bg
      │  lib/transport/http-link.js  ── HTTP + SSE ──┐
      │                                             │
      └─（审计 / 记忆 / 设置文件，见 §九）            │
                                                    ▼
虚拟机 192.168.1.50（VMware，Win10 x64）
└─ uia-bridge.py  :8850   ← 一个微信号（机器人 wxid_example_bot_0000）
      │ 读：wechatauto.WeChatDB  → 直接读 xwechat_files 里的 SQLite
      │ 写：wechatauto.WeChatGUI → UIA 找到窗口 / 会话 / 输入框，粘贴 + 发送
      ▼
   微信 4.2.0.9
```

同机的辅助进程：

- `:8899` PowerShell 控制面（`/status`、`/run?c=<cmd>`）——只在运维/排障时用，插件不依赖它
- `:8891` `wx-groups.py`——给设置页列群用，返回 `{"ok":true,"groups":[{id,name}]}`

三个端口的生命周期互相独立：桥挂了不影响列群，列群挂了只影响设置页的"刷新列表"。

## 四、消息流水线

入站（`lib/pipeline.js` 的 `accept`）：

```
桥轮询数据库（0.8s）→ SSE /events → normalizeInbound
  → 丢弃开关：not-enabled / self / empty / duplicate
  → 白名单判定（policy.decide）：不在 allow 里 → drop(not-allowlisted)
  → 群聊额外判唤醒：没带前缀也没 @ → drop(no-mention)
  → 防抖合并（同会话 1200ms 内的多条并成一轮；群里每条带 "名字：正文"）
  → 会话（一会话一个 DSH agent，persona 走 systemPrompt）
  → 模型生成 → cleanReply（去 Markdown、截 300 字）→ 表情替换
  → 限流（每会话 6s、每分钟 6 条）→ transport.sendText(/sendFile)
  → 审计 + 记忆写入（会话日志 + 说话人画像）
```

出站被丢弃时一定带 `reason` 落审计，**不会静默吞消息**。限流是丢弃而不是排队——
宁可少回一条，也不在恢复后一次性喷出十条过期回复。

主动消息（模型主动发起、不是回复）走 `publish → onProactiveText` 这条旁路，
和回复共用同一套限流与审计。

## 五、它到底能做什么

- **私聊**：名单上的人发什么，AI 都回（仍然会去重、限速，不会刷屏）。
- **群聊**：只有带了唤醒前缀（默认 `!`）才会理，比如 `!在吗`；没带就当没看见。
- **能发表情**：回复里写 `[表情: 开心]`，插件会去图库里找一张对应的图发出去
  （发的是图片，不是微信表情包——表情包要在一堆格子里点选，位置一变就点歪）。
- **记得上下文**：一个微信会话对应一个 DSH 会话，聊天记录就是它记忆的来源。
- **有人格**：私聊一套人设、群聊一套人设，改 `persona/*.md` 立刻生效，不用重启。
- **有审计**：每条进出都记一行（时间、会话、字数、结果），默认**不记正文**。

## 六、它明确不做什么

这段比上面那段更重要。

- **不认识的人说话，不回**。白名单里只有稳定 ID（`wxid_...` / `...@chatroom`），没有通配符，
  没有"先回一句再检查"这种漏风的写法。名单外的会话连读都不读。
- **不在你不知情时抢前台**。`allowForegroundSend` 默认是关的；关着时它**拒绝启动**，
  而不是"先用别的方式凑合一下"。
- **不主动加好友、不拉群、不群发、不转发**，群聊里也不主动 @ 别人。
- **不把 token、二维码、密钥写进日志**。
- **失败就说失败**。发送前它会等你手停两三秒；等不到就把这条丢掉，绝不硬抢鼠标；
  发完如果没法确认，它会如实记一条"未确认"，而不是重发刷屏。

## 七、你在界面里能看到什么

插件挂了一个设置页（DSH 的「设置」里），五块：

- **群聊白名单**：把微信里现有的群列出来，勾谁就把谁加进名单。
- **唤醒前缀**：默认 `!`，可以改成你喜欢的字符。
- **表情频率**：少 / 正常 / 多 / 疯狂。
- **人格**：当前群聊、私聊各读的是哪个文件（只读，改文件即可）。
- **记忆**：会话记忆、人物画像各有多少份、存在哪（只读，删文件即清）。

保存之后设置存在自己的小文件里，**不会去改手写的配置文件**——配置文件里有注释、
有格式，让程序回写一定会弄坏它。

状态与设置接口：`GET /api/channel-wechat-bg/status`、
`GET|PUT /api/channel-wechat-bg/settings`（同一条 `connection.fetch.register`，按 method 分发）。

## 八、它的脾气（几个数字）

| 行为 | 数值 | 为什么 |
| --- | --- | --- |
| 连发几条合并成一轮 | 1.2 秒 | 你连打三句"在吗"，不该收到三条回复 |
| 同一会话最小间隔 | 6 秒 | 防止一口气刷屏 |
| 每分钟上限 | 6 条 | 同上 |
| 单条回复上限 | 300 字 | 超了截断，不拆成好几条连着发 |
| 发送前等空闲 | 2.5 秒 | 你还在打字，它就先不动手 |
| 等空闲的上限 | 90 秒 | 一直不空闲就丢掉这条，绝不硬抢 |

## 九、群里的它，跟私聊里它不是同一个

一个号在两种场合，本来就该是两个样子。私聊里它话多、爱撒娇；群里它更收着——
别人聊着它听着，被叫到才搭一句。所以群聊可以单独写一份人格：
`persona/<名字>-group.md`，写了就用它，没写就退回原人设加几条群规。

表情包也不用你提醒。开心、被逗笑、安慰人的时候它会自己配一张：回复里写
`[表情: 名字]`，通道会换成真的表情图——但不会只甩一张图不说话。

发表情的密度能调：**少 / 正常 / 多 / 疯狂** 四档，默认「多」。这不是同一个提示词
换个形容词，而是四段强度不同的规矩——「疯狂」档几乎每条都配一张（纯信息性的回答除外），
「少」档只在情绪一眼能看出来时才配。在设置页里选一档就生效，不用重启。

## 十、它知道谁在说话，也记得你是谁

群里好几个人说话，它看得见每句是谁说的——`小王：这版我改完了`，不是一坨分不清人的字。

跟 A 说过的事，它不会在 B 那儿说漏。每个会话有自己的记忆：最近聊了什么、有过哪些约定。
再往上一层，它还记得**人**：同一个人在私聊和群里是同一个人，名字、说话习惯、你们之间
重要的事，都记在同一个人的画像里。想让它记住什么，它会在回复里写一句 `[记住: ...]`——
这句不会发出去，存进记忆就完了；群里定的事，它记的是"跟谁定的"，不是"群说的"。

## 十一、桥的 HTTP 契约（`scripts/uia-bridge.py`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | `{ok, injected, foreground, accountId, wechatVersion, hwnd, allow[], sent, failed, idleMs}` |
| GET | `/events` | SSE，每条 `data: {chatId, chatKind, senderId, senderName, text, timestamp, mentionedBot}` |
| PUT | `/allow` | 推白名单 `{"chats":[{"id","kind":"dm"|"group","mentions":[...]}]}` |
| POST | `/send` | `{chatId, text, dryRun?}` → `{ok, chat, echo, elapsedSec, messageId?}` |
| POST | `/send-file` | `{chatId, path, dryRun?}`，path 是**客户机内**绝对路径 |

三条必须知道的语义：

1. **桥重启会清空 allow**，插件必须在重连后重推；只连不推，等于静默不工作。
2. 发送是"抢前台 + 等空闲"：空闲不足 2.5s 时会等，等到 90s 仍不空闲就**丢掉这条**并报错。
3. 发送在桥内用一把锁串行化。**锁一旦被一次卡死的发送占住，后面所有发送都会排队到
   超时**——这是历史上最像"插件坏了"的一种故障，见 §十三。

## 十二、配置与状态

宿主侧配置在 profile 的 `cordis.patch.yml`（条目 `channel-wechat-bg`）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 总开关。为 false 时所有发送直接失败，不是"不启动"而是"明确拒绝" |
| `transport.kind` | `uia` | `uia` / `pad` / `mock`；`wechatferry` 保留但会拒绝启动 |
| `transport.baseUrl` | — | 桥地址，如 `http://192.168.1.50:8850` |
| `allowForegroundSend` | `false` | **必须显式为 true**，否则 uia 传输拒绝启动 |
| `allow[]` | — | 白名单：`{id, kind, label, persona, reply, triggers[], enabled}` |
| `denyUnknown` | `true` | 未知会话一律丢弃；本插件不支持放行未知会话 |
| `rateLimit` | 6 / 6 / 1200 / 300 | 每会话间隔 s / 每分钟条数 / 防抖 ms / 回复字数上限 |
| `audit` | `wechat-bg-audit.jsonl` | 落盘位置；`logContent: false` 时只记元数据不记正文 |
| `personaDir` / `memoryDir` | 见下 | 人设 md 与记忆 json 的目录 |
| `stickerRate` | `more` | 表情频率：`few` / `normal` / `more` / `crazy` |
| `groupsUrl` | 空 | 列群服务地址，空则按桥的主机名 + `:8891` 推 |
| `memeDir` | 空 | 表情图目录；空则不发图，只摘掉 `[表情: xx]` 标记 |

设置页写的是**另一个文件**：`<DSH_HOME>/channel-wechat-bg/settings.json`
（`DSH_HOME` 为空时按 `DSH_PROFILE_DIR → cwd` 兜底）。规则很简单：
**设置页存过的群与表情档位覆盖配置文件；私聊条目永远只认配置文件。**
这样设计是因为 patch 是人手写的（带注释），让程序去改它迟早出事。

## 十三、故障模式与排查顺序

按"先怀疑哪一层"排序，这是踩出来的顺序：

1. **微信掉登录**（VM 重启后最常见）。判据：数据库 mtime 不再变化、
   `xwechat_files\<账号>` 不更新。处理：起微信 → 点「登录」→ **手机确认**
   （每次都要，没有免密）。
2. **桥的发送锁被占死**。判据：直接 `POST /send` 真发（不带 dryRun）200 秒不返回，
   而 `dryRun` 秒回。处理：重启桥（`restart.cmd`），并检查那次卡死的发送为何没返回。
   排查时**先绕开插件直接打桥**，这一条能立刻把故障切成"插件侧"还是"桥侧"。
3. **桥刚重启、allow 是空的**。判据：`/health` 的 `allow: []`。处理：`PUT /allow`
   或把插件 disable→enable 让它重推。
4. **SSE 连接反复断**（插件侧重连）。历史上这会造成消息丢失——已修：桥侧改成
   `peek` 快照 + 写成功后再 `drop`，断了不丢。
5. **微信客户端僵死**（窗口还在、库里不再写）。判据：`get_groups()` 与
   `get_sessions()` 里都没有新群/新会话。处理：重启微信客户端，不要怀疑代码。
6. **插件根本没收到事件**。判据：审计里有 `in` 但没 `out`，或桥日志没有"收到"。
   处理：确认插件是否被重载、`/status` 里 transport 是否 connected。

自愈：宿主有一个隐藏的计划任务（`WXA-VMGuard`，走 `wscript` 起，避免弹窗）每 90 秒
检查 VM 进程与桥是否健康；客户机侧 `WXA-BridgeWatch` 每分钟检查桥进程。两者都只做
"拉起"，不做"猜测性重启"。

## 十四、能力与限制

能：私聊/群聊收发文本、发图片（AI 里写 `[表情: 名字]` 会被换成真图）、群聊独立人格、
每会话 + 每说话人两层记忆、设置页改白名单/唤醒前缀/表情频率、审计。

不能（或不做）：语音/文件/小程序等富媒体入站、多账号并行、群管理动作、真正的后台发送
（微信 4.x 没有可用协议层）、跨设备同步历史。

性能：一次发送 2~20 秒（等空闲 + UIA 操作），受机器负载影响；同一会话 6 秒内不会发第二条。

## 十六、想自己跑起来

1. 一台 Windows 虚拟机（VMware），里面装微信 4.x 和 Python 3.11。
2. 把 `scripts/uia-bridge.py` 放进去，跑起来（默认监听 8850）。
3. 在 DSH 里装这个插件，把 `transport.baseUrl` 指到那台虚拟机，
   打开 `allowForegroundSend`，白名单填上你的会话 ID。
4. 重载插件，确认 `/health` 的 `allow` 里有你的会话。
5. 自己给自己发一句话，看审计里 `in → out` 成对出现。

细节在 [README.md](../README.md) 和 [TRANSPORT.md](../TRANSPORT.md)，
三种传输各自的前置条件、风险、封号说明都在后者里。
